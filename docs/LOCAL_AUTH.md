# MacでのGoogleログイン設定

## 設定する項目

`.env.local` は利用者自身で編集してください。接続情報や秘密の値をチャットやGitに貼る必要はありません。

| 環境変数名 | 用途 |
| --- | --- |
| `AUTH_GOOGLE_ID` | Google CloudのOAuthクライアントID |
| `AUTH_GOOGLE_SECRET` | 同じOAuthクライアントのクライアントシークレット |
| `AUTH_SECRET` | ログイン状態の暗号化に使う、32文字以上の十分にランダムな秘密の値 |
| `AUTH_URL` | このアプリを開くアドレス（Macでは `http://localhost:3000` に統一） |
| `ALLOWED_EMAILS` | 許可するメールアドレス。複数の場合はカンマで区切る |
| `DATABASE_URL` | 既存のNeon接続設定。今回の認証追加では変更しない |

`AUTH_SECRET` はGoogleのクライアントシークレットとは別の値です。
許可メールアドレスは前後の空白と英字の大小をそろえて照合し、別名やドメイン単位では許可しません。
`ALLOWED_EMAILS` が空または未設定の場合は全員を拒否します。
設定不足の場合はログインボタンを無効にし、カウンターAPIも拒否します。

## Google Cloudで確認すること

OAuthクライアント `click-counter-local` の「承認済みのリダイレクトURI」に、次を登録します。

`http://localhost:3000/api/auth/callback/google`

`localhost` と `127.0.0.1` は異なるアドレスです。通常のローカル利用では、ブラウザ、`AUTH_URL`、Google側の登録を `localhost:3000` に統一します。
Googleのテストユーザー登録とアプリの `ALLOWED_EMAILS` は別の制限です。テスト中は両方に登録が必要です。

設定後に開発サーバーを再起動し、`http://localhost:3000` を開きます。
GoogleのパスワードはGoogleの画面にだけ入力してください。

## 保護する範囲

- Googleの確認済みメールアドレスが許可リストにある場合だけログインできます。
- ページとGET・POST・DELETEの各要求で、サーバーがログイン状態と現在の許可リストを確認します。
- 許可リストから外した場合は設定を反映して再起動すると、既存のログイン状態でも次の要求を拒否します。
- APIは未ログインなら401、許可なしなら403、認証設定不足なら503を返し、DBへアクセスしません。
- 加算・リセットには同じアプリからの要求であることを示すOriginも必要です。
- カウンターAPIの結果は保存して使い回さない設定です。
- ログイン状態はAuth.jsの暗号化Cookieで管理し、Neonに認証用の表を作りません。
- 数字は従来どおり、許可された利用者全員で1つを共有します。

Neonの管理画面や接続情報を持つ人の直接アクセスは、このアプリのログイン機能とは別に管理してください。
ダウンロードしたGoogle認証情報の `client_secret_*.json` はGitの対象から除外しています。

## 実装の構成

- `auth.ts`: Auth.js、Google認証、ログイン時の許可判定
- `lib/auth-policy.ts`: 環境変数の確認とメールアドレスの照合
- `lib/access.ts`: リクエストごとのサーバー側の利用許可確認
- `app/api/auth/[...nextauth]/route.ts`: Googleログインの受付
- `app/auth-actions.ts`: ログインとログアウト
- `app/login/page.tsx`: ログイン画面と設定不足・拒否時の案内
- `app/page.tsx`: 利用許可を確認してからカウンターを表示
- `app/components/counter.tsx`: 既存のカウンター画面（ログアウトを追加）
- `app/api/count/route.ts`: 既存SQLの前に利用許可とOriginを確認
- `types/next-auth.d.ts`: Googleで確認済みであることを表す型
- `tests/auth.test.mjs`: 実際のDBを使わない認証・APIのテスト
- `tests/auth-http.mjs`: テスト専用サーバーと暗号化Cookieを使うHTTPテスト

Next.jsのCache Componentsが有効なため、ページの認証確認はSuspense内で行い、認証結果を共有キャッシュに保存しません。
Auth.jsはNext.js 16とReact 19に対応する `next-auth@5.0.0-beta.32` を固定しています。
これはAuth.js公式導入手順で案内されるv5のベータ版です。

## 確認方法

`npm test` はGoogleやNeonへの接続を偽物に差し替えたテストです。
未ログイン、許可外、設定不足、許可の取り消し、外部サイトからの更新拒否を確認します。
`npm run lint` と `npx tsc --noEmit --incremental false` でソースの検査ができます。

`node tests/auth-http.mjs` は、テスト専用の設定でMac内のポート3101にサーバーを起動し、実際のAuth.jsと暗号化Cookieを通した拒否動作を確認します。
本物のDB接続情報は無効なテスト値で上書きされ、終了時にサーバーを停止します。
同時に別の開発サーバーを起動せずに実行してください。
このHTTPテストは専用の `127.0.0.1:3101` を使用します。通常のログイン確認に使う `localhost:3000` とは別であり、`.env.local` の変更は不要です。

## 確認済みの結果（2026年10月24日時点）

- Next.jsを `16.4.0` から `16.4.3` に更新し、インストール済みのバージョンも確認しました。`eslint-config-next` も `16.4.3` にそろえています。
- 利用者によるブラウザ確認で、Googleログイン・ログアウトと未ログイン時のAPIアクセス拒否が成功しました。
- 更新後の `npm test` は9件すべて合格、失敗0件でした。表示上の9件は、全体をまとめる1件と個別の確認8件です。ホワイトリスト外の拒否、許可の取り消し、DBアクセス前の拒否などを確認しています。
- 更新後の `node tests/auth-http.mjs` は5項目すべて合格しました。未ログインの拒否、ホワイトリスト外の拒否、メール確認がない利用者の拒否、不正なCookieの拒否、別サイトからの更新要求の拒否を確認しています。
- `npm run build -- --webpack` による本番用ビルドは成功しました。TypeScriptの検査とページ生成も完了しています。
- `npm run build` によるTurbopackの本番用ビルドは未完了です。最初はGoogle Fontsへの通信エラー、その後はCSS処理中の内部通信用ポート作成で `Operation not permitted` が発生しました。実行制限の外での再実行でもポート作成エラーが再現しています。原因が実行環境の制限か、Turbopack側の問題かは確定していません。

自動テストには代用品または無効なDB接続先を使用しました。本番用ビルドの確認でも、実行中だけDB接続先と認証情報をテスト値に置き換え、本物のNeon DBへの接続やデータ変更は行っていません。秘密の設定ファイルも変更していません。
ビルド成功は、本番用ファイルを生成できたことの確認です。実際のGoogleログインやNeon DB接続の動作確認とは別です。

Webpackはコマンドの `--webpack` で今回だけ指定しています。`package.json` のビルド命令は `next build` のままで、恒久的な切り替えは行っていません。VercelでWebpackへの切り替えが必要かは未確認です。ビルドだけでは公開されません。

実装当時はlintとTypeScriptの検査も成功しています。また、当時の依存関係監査ではESLint関連の開発用依存関係にhigh警告5件があり、追加したAuth.js関連の警告はありませんでした。これは過去の記録であり、Next.js 16.4.3への更新後の監査結果ではありません。
